两者都能接入大模型、检索、API 和状态存储。关键区别是行动如何编排；权限、业务校验和运行边界始终需要程序落实。

本文比较两套通用设计：预设流程驱动的 Bot，以及Agent 驱动的 Bot。下文的“原架构”和“新架构”分别指这两个比较模型；模块图和 VPN 工单案例是参考设计，便于理解各组件如何配合。

Bot：用户从哪里与系统交互

本文用它指聊天机器人这种产品和入口形态，例如网页、企业 IM 或消息平台。入口内部可以接规则、工作流，也可以接 Agent。

Workflow：步骤如何被组织

开发者定义节点、分支和状态转移。节点内可以运行模型、检索资料或调用工具，也可以等待用户、循环和重试。

LLM Agent：下一步如何被选择

模型结合目标、上下文和执行结果，参与选择下一步行动；运行时负责把这些选择变成受约束的实际执行。

本文采用的 workflow / agent 区分，可参照 LangGraph 的流程与 Agent 说明。因此，使用 LLM、工具或多轮对话，本身不足以判断系统是否采用 Agent 执行方式。

一、原架构：预设流程驱动的 Bot

01

开发者定义业务路径，运行时根据输入和状态选择已经定义好的分支。

组件主要职责
接入与会话验证来源和身份，处理重复消息，装载当前会话。
意图路由把问题归到已支持的业务类型，选中相应流程。
工作流 / 状态机决定当前节点、缺失字段、条件分支，以及下一次转移。
业务处理器封装校验、检索和 API 调用，处理已经设计过的异常。
状态与输出保存已收集的信息和执行结果，组织回复或等待下一轮输入。

例如，Rasa 的 flows 将所需用户信息、API / 数据库访问和分支条件写入业务逻辑。这说明流程式 Bot 可以拥有完整的多轮业务能力。图中的认证、消息去重等接入模块是本文补充的工程设计。参考：Rasa Business Logic with Flows

1.1 原架构的运行逻辑

以用户请求“公司 VPN 连不上，帮我排查并登记工单”为例，一条预设业务路径可以这样运行：

  1. 接入消息，验证身份，读取本轮对应的会话与流程状态。
  2. 识别 VPN 故障意图，进入已经配置好的排障流程。
  3. 检查操作系统、错误码等必填信息；缺少时保存进度并追问。
  4. 按照预设节点查询服务状态、匹配排障资料，再走相应分支。
  5. 满足工单字段、授权和业务条件后调用创建接口，保存实际回执。
  6. 返回处理结果；异常进入预设重试、失败说明或人工交接路径。

流程固定，仍然可以有分支、循环和模型调用。 这里的“固定”指可执行路径和转移规则由开发者定义；模型输出和外部服务结果仍可能变化。

二、新架构：Agent 驱动的 Bot

02

Bot 保留消息入口，内部加入能够管理任务与模型行动循环的 Runtime / Harness。

组件主要职责
上下文组装提供用户目标、已知约束、必要历史、工具说明和本轮观测。
LLM 决策选择直接回答、询问用户、调用工具，或调整后续行动。
Runtime / Harness组织执行循环，检查权限、预算、超时、取消及最大轮数，记录运行状态。
工具执行器校验参数，调用具体函数或服务，返回结构化的成功、失败或结果待确认信息。
任务状态记录当前进展、已尝试的动作、执行回执和等待原因；需要恢复时使用持久化机制。

Agent 常通过“行动—环境反馈—再选择”的循环处理开放任务。是否输出显式长计划、是否设置专门规划器，可以按任务选择；单个模型配合少量工具也能构成这种执行方式。参考：Anthropic Building effective agents

2.1 新架构的运行逻辑

  1. 初始化任务：确认目标、身份、允许使用的工具和运行上限。
  2. 组装上下文：装载本次任务需要的状态、资料和历史结果。
  3. 选择行动：模型可以回答、追问，也可以生成工具调用请求。
  4. 受控执行：Runtime 检查参数和权限；需要人工判断的动作进入等待状态。
  5. 观察结果：记录工具真正返回的内容，更新进度，再决定后续步骤。
  6. 返回或暂停：达到任务目标后返回；缺少用户信息时等待；遇到限制、取消或无法恢复的错误时明确结束状态。

三种状态要分开：模型生成了调用请求，表示它选择了某个动作；工具返回成功回执，表示动作执行结果已知；用户目标是否达成，还需要结合业务规则、证据或人工评估判断。

2.2 状态、记忆与恢复

对话消息、任务执行状态和长期记忆用途不同。任务状态记录进度与执行结果；跨任务有价值的偏好才适合进入长期记忆。LangGraph 的持久化文档也分别讨论了线程状态检查点与跨线程存储。持久化需要应用接入实际存储，不能把进程内历史当作可靠的崩溃恢复机制。参考：LangGraph Persistence

创建工单时还有一个两套架构都要处理的问题：接口超时可能只是回执丢失，工单已经创建。重试应通过业务幂等键或结果核对避免重复创建。检查点和对话记忆不能自动保证外部操作只发生一次。参考：AWS 关于幂等 API 与安全重试的说明

三、架构差异与优缺点

03

比较同一业务目标下的控制方式和工程代价，不把某种组件当作 Agent 独有能力。

维度预设流程 BotAgent Bot
下一步由谁决定主要按程序定义的节点和转移规则执行。模型结合目标和中间结果提出后续行动，Runtime 控制实际执行。
任务边界适合步骤和异常类别较明确的任务。适合所需步骤难以预先列全、需要动态探索的任务。
LLM 与工具都可以使用，调用顺序主要被流程约束。都可以使用，部分选择与顺序由模型动态决定。
状态管理会话字段、流程节点、业务记录。通常还需组织任务进展、行动历史和执行结果；长期记忆按需配置。
异常处理已设计的重试、回退和人工交接路径较清晰。可根据反馈尝试其他线索，也需防止无效重试和错误积累。
可预测性编排路径较可预测；模型与外部数据仍可能使结果变化。行动路径和调用次数可能变化，调试需要完整执行轨迹。
成本与时延步骤较明确时较容易估算；复杂流程也可能昂贵。动态轮次增加估算难度；实际开销取决于任务、模型和工具。
测试重点节点、分支、字段校验及端到端流程。还要评估工具选择、任务成功、停止条件和不同执行轨迹。
权限与审计在程序与工具接口中落实。同样在程序与工具接口中落实，模型不能自行批准越权动作。
维护代价业务分支增多时，流程图和规则维护负担上升。工具契约、上下文、评估集和 Runtime 的维护负担上升。
A+预设流程的优势

路径清晰，容易围绕明确业务规则审查、测试和估算运行成本，适合稳定的标准流程。

A−预设流程的代价

需要提前覆盖分支；开放问题和例外增多后，流程容易膨胀，新增能力常需调整编排。

B+Agent 的优势

可根据中间结果调整工具和行动顺序，更适合信息不足、路径多变的调查与综合任务。

B−Agent 的代价

增加决策不确定性、潜在无效循环与排错难度，需要更细的执行观测和运行边界。

这些是设计取舍，不能直接推出某个实现更快、更便宜或成功率更高。采用更复杂的模式，需要通过业务评估证明收益。参考：Anthropic 对复杂度、成本与任务表现的讨论

3.1 同一个 VPN 工单请求，两套架构怎样处理

情况预设流程 BotAgent Bot
用户没有给错误码必填字段检查触发追问。模型判断需要补充，或先查已获授权的服务状态；不能臆造缺失字段。
VPN 服务正常，但用户仍无法连接进入事先设计的客户端或网络排障分支。结合现有结果选择下一条可用线索；可执行范围受提供的工具限制。
查询接口失败按预设策略重试、回退或交接。在运行边界内重试或选择其他信息源；无法继续时明确说明。
创建工单接口超时两者都应核对结果或使用业务幂等键，避免重复创建；未确认成功时不能声称已经登记。

四、怎样选择：按任务拆分控制方式

在这个参考设计里，可以保留统一的 Bot 接入、身份校验和业务 API，把开放调查交给受控 Agent，把明确的交易或审批环节保留为程序流程：

统一接入与任务路由 → 固定工作流或受控 Agent → 业务校验与必要审批 → 受控执行 → 真实结果反馈

例如，Agent 动态完成 VPN 排障调查；创建工单仍经过固定字段校验、授权和幂等接口。选择混合方式的依据是业务需要，而不是对“新架构”的形式要求。微软的编排指南也讨论了模式组合，以及单 Agent 足以解决问题时避免额外协作复杂度。参考：Azure AI agent orchestration patterns

  1. 步骤明确、规则稳定：优先评估预设流程，例如资料收集、规则查询、表单提交与明确的审批流。
  2. 路径随证据变化：评估 Agent，例如故障排查、多源资料综合、需要不断补齐信息的任务。
  3. 任务同时包含两类环节：在同一系统内组合工作流与 Agent，把职责和交接条件定义清楚。
  4. 用相同任务集比较：记录端到端成功率、人工接管率、错误操作、调用次数、P50 / P95 时延和单个成功任务的总成本。

队列取决于耗时和并发需求，长期记忆取决于跨任务信息的价值，多 Agent 取决于分工收益，MCP 则是一种工具接入协议选择。这些能力都可以与工作流结合，也不是单个 Agent 的必要组成。
