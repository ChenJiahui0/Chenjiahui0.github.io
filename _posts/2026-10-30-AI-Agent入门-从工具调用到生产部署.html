一句话掌握全篇
理解目标 → 调用工具 → 检查结果 → 继续行动

AI Agent 的核心，是让大模型围绕一个目标，结合上下文选择工具、执行动作，再根据结果决定下一步。理解这件事，需要同时关注模型、数据、工具和整个任务的运行过程。

这篇笔记按 Microsoft Developer 的 Full Course (Lessons 1-10) AI Agents for Beginners 整理课程主线，并参考同系列的同期官方讲义。视频发布于 2025 年 3 月 24 日，全长约 64 分钟，使用旅行助手串起 Agent 的主要概念。

文中的框架定位按视频发布时的语境记录，讲义链接固定到 2025 年 3 月的课程版本。本文侧重概念与设计方法，具体 SDK 写法应结合使用版本核对；末尾的实践顺序是个人归纳。

一、Agent 的基础：模型、记忆与工具

01

三个基础组件：大模型、记忆与工具。

00:00 ↗

课程开头从三个部分解释 Agent：

大模型（LLM）

理解用户的意图，根据已有信息决定行动步骤。

记忆（Memory）

保存当前任务的上下文，以及后续可能复用的偏好和经验。

工具（Tools）

读取外部信息或执行动作，例如查询目的地、检索文档、调用业务 API。

旅行助手接到“帮我规划一次旅行”的请求后，需要理解目的、获取可用信息，再给出方案。用户补充偏好或否定建议时，这些信息也应该影响后续选择。

视频的开场示例把一组目的地封装成工具。用户要求换个去处时，助手结合前面的对话给出另一个建议，展示了模型、工具和短期记忆怎样一起工作。

这里的记忆可以分为两层：短期记忆保存这轮对话和任务状态；长期记忆保存跨任务仍有价值的信息，例如用户的出行偏好。长期记忆需要应用负责存储、检索和更新，不能假定模型会自动记住每次交流。

从系统角度看，Agent 还需要一个明确的运行环境：能读取什么状态、允许执行哪些动作、完成任务后如何获得反馈。这些条件共同决定它的能力范围。第一课官方讲义

下面是对这条运行主线的概念归纳：

理解任务读取用户目标与上下文
→
选择行动规划步骤与可用工具
→
调用工具校验参数并执行操作
→
评估结果更新状态并判断下一步

达到目标：返回结果；信息不足：继续行动；达到运行边界：说明限制或请求人工介入。

开放式、多步骤、需要依据反馈调整的任务，更能体现这种结构的价值。对于步骤固定的简单任务，也应先考虑普通函数或确定性的工作流是否已经足够。

二、框架管理的是任务运行过程

02

先明确任务需要，再选择框架和托管服务。

05:55 ↗

接入模型只是 Agent 开发的一部分。应用还要管理上下文、工具描述、执行状态、多个角色之间的消息，以及日志和评估。框架把这些共性能力组织起来，减少重复实现。

视频介绍了当时微软生态中的三种选择：

框架或服务 课程中的定位 理解重点
Azure AI Agent Service 托管 Agent 服务 管理 Agent、线程、消息和内置工具，并连接 Azure 服务
Semantic Kernel 面向企业应用的编排 SDK 通过连接器、插件等组织模型与业务能力
AutoGen 偏重研究与实验的 Agent 框架 探索多 Agent 的消息交互和协作方式

它们承担的职责有所不同，托管服务也可以与编排框架结合使用。这张表记录的是 2025 年课程中的介绍，不作为当前产品能力的完整比较。

选型时更有用的问题是：当前任务需要几个 Agent？哪些工具必须接入？上下文由谁维护？如何观察一次执行？框架提供不同的组织方式，具体选择需要结合任务复杂度和运行要求评估。第二课官方讲义

三、设计 Agent，要让用户理解并控制它

03

让用户知道 Agent 能做什么、正在做什么，以及如何介入。

14:14 ↗

第三课把视角转向用户体验。Agent 可能连续执行多个步骤，甚至在后台处理任务，因此用户需要知道它具备哪些能力、正在做什么，以及何时能够介入。

同期讲义把落地原则概括为透明、控制和一致性：

01透明

说明 AI 的身份、能力、限制和任务状态。

02控制

允许用户补充偏好、修正结果、提供反馈，以及管理历史信息。

03一致性

使用用户熟悉的交互，让同一种操作保持可预期。

以旅行助手为例，用户应该能区分“正在查询可用航班”“已生成候选方案”和“预订已完成”这些状态。明确的状态能帮助用户判断下一步，也能减少对 Agent 能力的误解。

这些设计原则是架构和交互的起点。把后台执行过程、反馈入口和人工介入方式一起设计，才能让任务推进过程保持可理解。第三课官方讲义

四、工具调用：把模型的选择连接到真实执行

04

模型提出调用请求，应用负责校验与执行。

19:35 ↗

工具使用模式让 Agent 获得外部能力。工具既可以是简单函数，也可以是数据库查询、搜索服务、业务 API 或代码解释器。

一次典型的工具调用包含以下步骤：

01

应用向模型提供工具名称、用途和参数结构。

02

模型根据用户请求，生成工具调用请求和参数。

03

应用校验请求，并运行相应函数或服务。

04

应用把工具结果送回模型。

05

模型结合结果回答用户，或选择下一个动作。

模型产生调用请求，应用负责实际执行。 因此，看到模型返回工具名和参数时，还需要确认执行是否成功，以及返回数据是否满足任务要求。

工具的名称、描述和参数定义会影响模型的选择。将“列出目的地”和“查询某个目的地是否可预订”拆成用途清楚的工具，就能让应用分别处理不同意图。

工具层也承担业务约束：检查参数是否合法、执行权限是否足够、服务失败后怎样返回错误。尤其是数据库和有副作用的操作，需要由程序与权限系统落实边界。第四课官方讲义

五、Agentic RAG：根据信息缺口继续行动

05

信息不足时，继续检索、改写查询或切换工具。

25:47 ↗

RAG，即检索增强生成，将检索得到的资料放入模型上下文，帮助模型利用外部知识回答问题。一个基础流程可以表示为：用户提问、检索相关资料、组织答案。

Agentic RAG 进一步让 Agent 判断：当前资料是否足够？缺少哪些信息？应该改写查询、继续检索，还是调用另一种工具？

例如，一份旅行文档可以说明某地适合什么活动，但用户还关心温度或可用航班。Agent 可以把文档检索与其他工具组合起来，补齐回答所需的信息。

维度 基础 RAG 流程 Agentic RAG
执行路径 常见实现采用预设检索流程 根据中间结果决定后续动作
信息来源 按预设方式访问知识源 可组合检索、数据库与 API 等工具
资料不足时 依赖既定的缺失处理方式 可继续查询、切换工具或寻求帮助
状态管理 取决于具体实现 通常需要记录已尝试的步骤与结果

这里比较的是课程用来说明概念的基础流程。普通 RAG 系统也可以加入重试、查询改写等能力；Agentic RAG 的重点在于，利用 Agent 动态组织这些步骤。

多轮检索增加了补充证据的机会，也增加了成本和错误传播的可能。系统仍需设置终止条件，并保留信息来源与执行记录，方便判断答案是否有依据。第五课官方讲义

六、可信 Agent：提示词、权限与人工参与

06

把提示词、权限、运行边界和人工参与一起设计。

33:03 ↗

工具越多，Agent 能影响的系统也越多。第六课关注如何让这些能力按预期运行。

首先，需要明确的系统消息，说明角色、责任、任务范围和行为规则。同期讲义还介绍了用模板生成系统消息，再通过评估持续调整的方法。

其次，需要系统层面的约束：

01最小权限

为工具和数据配置完成任务所需的最小权限。

02可信知识源

保护知识源，降低错误或被篡改的信息进入流程的风险。

03运行上限

限制调用次数和运行轮次，避免资源持续消耗。

04故障处理

为外部服务失败准备隔离、重试或回退方式。

05人工参与

在适当环节让用户反馈、批准或终止任务。

这也是 Human-in-the-loop 的作用：把人的判断接入任务执行过程。对于旅行助手，用户可以在方案生成后修正偏好，再决定是否继续后续操作。

系统消息、权限控制、运行边界和人工参与需要共同发挥作用。提示词能够描述规则，程序和服务还需要落实这些规则。第六课官方讲义

七、规划模式：让复杂目标成为可管理的步骤

07

明确目标，拆分子任务，再根据执行结果调整计划。

38:54 ↗

当用户的目标涉及多个动作时，可以先生成计划，再组织执行。

以“三天的旅行安排”为例，任务可能包含确定偏好、查询航班、选择酒店、安排交通和活动、汇总行程。规划需要考虑每一步的输入、依赖关系、使用的工具，以及完成后交付什么结果。

同期讲义用结构化计划说明这一过程。通过 JSON 等格式，系统可以明确记录子任务和负责它的 Agent，便于下游解析与分派。

计划还要随执行结果调整。酒店不可用、航班时间发生变化，或者用户新增限制，都可能使原计划失效。执行中的反馈应该回到规划阶段，推动局部修改或重新规划。

需要分清三个状态：计划已生成、动作已执行、目标已达成。它们分别需要不同的证据。结构化输出帮助系统传递计划，工具返回值说明动作结果，任务评估则判断最终是否满足用户目标。第七课官方讲义

八、多 Agent：分工之外，还要设计协作

08

分清角色、共享约束，并约定交接与终止方式。

44:20 ↗

多 Agent 系统让不同角色围绕共同目标工作。旅行场景可以分为航班、酒店、活动规划等角色，由协调者分派任务并汇总结果。

这种拆分有助于限定每个角色的职责和工具范围。它也带来新的问题：各角色如何通信？共享哪些上下文？日期和预算怎样保持一致？一个任务失败后，其他任务如何处理？

同期讲义介绍了群聊、交接等协作方式。无论采用哪种方式，系统都需要明确：

  1. 谁负责当前子任务，谁负责最终结果。
  2. 交接时要传递哪些信息。
  3. 如何判断子任务完成，以及何时停止协作。
  4. 用户可以在哪些环节介入。

运行日志也要能够还原每个 Agent 的行动和信息流。只有看清各角色的贡献与开销，才能判断增加 Agent 是否改善了任务结果。第八课官方讲义

九、元认知：把反馈用于调整决策策略

09

通过评估和反馈，改进下一次的决策策略。

51:22 ↗

第九课使用 Metacognition，也就是元认知，讨论 Agent 如何评估自己的选择并调整后续策略。

从工程角度，可以把它理解为一个反馈循环：明确目标，执行任务，评估结果，记录问题，再调整下一次行动。

同期讲义中的酒店推荐示例很直观：最初按低价选择酒店，得到质量不符合要求的反馈后，修改价格与质量的权衡方式。类似地，如果用户不喜欢拥挤景点，后续推荐也应调整筛选依据。

这里可以区分两种改进：一种是修改当前答案，另一种是修改产生答案的策略。后者需要保存有用的反馈，并在之后的检索、排序或规划中重新使用。

这种适应过程可以通过上下文、记忆和程序逻辑实现，并不必然涉及模型参数更新。对自我评估的结果，也应该结合工具数据、用户反馈和明确标准来检查。第九课官方讲义

十、生产部署：评估整个任务链路

10

评估整个任务链路，再比较质量、耗时和成本。

58:32 ↗

最后一课将重点放在持续评估和运行管理上。Agent 涉及模型、工具、外部服务与用户交互，排错也需要沿着这些环节展开。

评估环节 需要观察的问题
模型与服务请求 连接是否成功，响应时间是否合理？
意图理解 Agent 是否识别了用户真正要完成的任务？
工具选择 工具和参数是否适合当前目标？
工具执行 是否报错，返回的数据是否完整可用？
结果组织 回答是否正确使用工具结果并满足约束？
用户反馈 用户能否指出问题，反馈是否进入改进流程？

记录这些评估点，有助于比较模型、提示词或工具变更前后的效果。例如，工具选择错误时，需要检查工具描述和调用逻辑；服务返回异常时，需要检查执行与回退机制。

运行管理还包括终止条件和成本控制。同期讲义讨论了缓存、对合适任务使用较小模型，以及根据复杂度进行模型路由。应用应通过具体业务的评估结果判断这些调整是否可接受，并考虑缓存数据的时效性。

这门课提供的是生产化思路概览。真正落地时，还需要把评估、监控、错误处理和用户反馈接到完整业务流程中。第十课官方讲义

我的实践思路

结合这十课，我会按下面的顺序做一个小型 Agent 项目。以下是对课程内容的实践归纳：

  1. 先定义一个具体任务。 写清输入、成功条件、允许使用的数据和工具。例如，只完成“根据日期和预算生成候选行程”。
  2. 用单 Agent 跑通工具调用。 先接少量用途清楚的工具，检查参数、返回值和错误处理。
  3. 补齐状态与反馈。 保存用户已给出的条件、执行过的步骤和当前缺口，让任务能够继续推进。
  4. 按实际困难引入设计模式。 知识不足时加入检索，任务复杂时加入规划，存在清晰分工时再尝试多 Agent。
  5. 建立可重复的评估。 覆盖成功、缺少信息、工具失败和用户改需求等情况，再比较质量、耗时与成本。

对后端开发而言，可以从一个熟悉的切入点开始：把工具当作受约束的服务接口，把任务状态当作需要维护的数据，把评估当作贯穿调用链路的检查。模型提供了理解自然语言和选择行动的能力，应用则负责让这些行动能够可靠地执行。
